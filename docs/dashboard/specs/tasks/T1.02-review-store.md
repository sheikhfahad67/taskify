# T1.02 — review-store.mjs reads and safely writes review.json, even with two writers at once

## Objective

`dashboard/lib/review-store.mjs` is the only code that writes `review.json`. The server (T1.04) and
the CLI (T1.06) both use it. It reads a missing or broken file as an empty review, validates input
against `01` §2c, and writes under a lock with temp-file-plus-rename, so two processes writing at
the same moment never lose an update or leave a half-written file.

## Scope

### Create
- `dashboard/lib/review-store.mjs` — exports:
  - `readReview(planDir) → { version: 1, comments: [], approvals: [] }` — never throws; a missing,
    empty, or invalid file returns the empty shape.
  - `addComment(planDir, { file, anchor, text, author }) → comment` — validates per `01` §2c
    (`file` must be a relative `.md` path with `/`, no `..`, and must exist inside `planDir`);
    throws an `Error` with `code = 'EINVAL'` on bad input.
  - `resolveComment(planDir, id, { note, by }) → comment` — `code = 'ENOENT'` if the id is unknown.
  - `addApproval(planDir, { note, by }) → approval`.
  - `reviewSummary(planDir) → { approved, approved_at, docs_changed_since_approval, open_comments, resolved_count }`
    (`docs_changed_since_approval` = plan-root files matching `/^\d\d-.*\.md$/` with `mtime` after the
    latest approval).
  Lock, temp-file, rename and retry behaviour exactly as `01` §2c. Creates `<planDir>/.taskify/` if missing.
  Imports only `node:` modules.
- `dashboard/test/review-store.test.mjs` — tests named below.

### Explicitly out of scope
- HTTP handlers — T1.04. CLI commands — T1.06.
- Editing any plan doc or spec — never, by any task.

## Implementation steps

1. Implement the store per Scope.
2. Tests (exact names): `readReview returns empty shape for missing or broken file`,
   `addComment validates and appends`, `addComment rejects path escape and non-md`,
   `resolveComment sets resolved fields`, `resolveComment unknown id throws ENOENT`,
   `addApproval and reviewSummary`, `stale lock is removed`, `two processes writing at once lose nothing`.
3. The concurrency test spawns 2 child Node processes (`process.execPath`, no shell) that each call
   `addComment` 20 times on the same temp plan copy, waits for both, then asserts 40 comments with
   40 unique ids and that `JSON.parse` of the file succeeds.
4. The `reviewSummary` test sets the approval time, then uses `fs.utimesSync` to make
   `00-overview.md` newer and asserts it appears in `docs_changed_since_approval`.

### Findings

- **R-1** — **Severity:** Important
  - **Claim:** two `continue` paths in `acquireLock` (stale-lock unlink fails; `wx` fails EPERM/EBUSY with no lock file → stat ENOENT) skip the deadline check and the sleep, so the loop can spin forever at 100% CPU and freeze the synchronous server.
  - **Evidence:** review-store.mjs:41-50 (`continue` at :44, :47; deadline at :49).
  - **Required fix:** check the deadline on every pass (top of loop after a failed `wx`); sleep on the `continue` paths too.
- **R-2** — **Severity:** Important
  - **Claim:** `update()` reads through tolerant `readReview`, so a write over an unparseable, wrongly shaped, or unreadable (EACCES/EBUSY) review.json replaces all existing comments/approvals with just the new one.
  - **Evidence:** review-store.mjs:20-28, 73.
  - **Required fix:** in `update`, treat only ENOENT or an empty/whitespace file as empty; on any other read/parse/shape failure throw (`code = 'ECORRUPT'`) and leave the file untouched. `readReview` stays tolerant (spec Objective). Add a test: `{not json` → addComment throws, file unchanged.
- **R-3** — **Severity:** Minor
  - **Claim:** stale-lock removal is a check-then-act race; two writers can both remove a stale lock and both enter.
  - **Evidence:** review-store.mjs:42-45.
  - **Required fix:** optional (owner token in lock) or record as follow-up.
- **R-4** — **Severity:** Minor
  - **Claim:** `finally` unlinks the lock without checking ownership.
  - **Evidence:** review-store.mjs:79-85.
  - **Required fix:** optional (same token) or follow-up.
- **R-5** — **Severity:** Minor
  - **Claim:** tmp file left behind when write/rename fails.
  - **Evidence:** review-store.mjs:75-77.
  - **Required fix:** `rmSync(tmp, {force:true})` then rethrow.
- **R-6** — **Severity:** Observation — `file` not normalised (`./x.md`, `a//x.md` accepted); traversal correctly blocked.
- **R-7** — **Severity:** Observation — synchronous Atomics.wait design acceptable once R-1 is fixed.
- **R-8** — **Severity:** Observation — unknown-id resolve, lock release paths, validation-before-lock all correct.

**Round 2 (2026-10-05):** verdict **`approved`**. R-1, R-2, R-5 fixed (lock loop bounded at ~2 s; `readForWrite` throws ECORRUPT and leaves the file untouched; tmp cleaned). R-3/R-4 deferred to Follow-ups. Suite re-run by orchestrator: 17 pass, 0 fail.
