# T1.08b — The login cookie is named per port, so two dashboards on 127.0.0.1 keep separate logins

Inserted after the Phase 1 gate at the user's request (2026-10-05), before the UI is built. Plan
doc `01` §3 was updated by the user's decision to name the cookie `taskify_t_<port>`.

## Objective

`GET /?t=<token>` sets `taskify_t_<port>=<token>; HttpOnly; SameSite=Strict; Path=/` (plus `Secure`
behind `X-Forwarded-Proto: https`), where `<port>` is the port the server actually bound. The auth
check reads only the cookie with that exact name; a `taskify_t` or `taskify_t_<other port>` cookie
in the same request is ignored. So two servers on 127.0.0.1 with different ports and tokens each
accept their own cookie and reject the other's, even when the browser sends both cookies to both.
Bearer auth is unchanged.

## Scope

### Edit
- `dashboard/server.mjs` — cookie name in the `Set-Cookie` header and in the cookie-reading regex
  becomes `taskify_t_${port}` (the bound port, known after `listen`).
- `dashboard/test/server-read.test.mjs` — update the existing cookie assertions to the new name
  (keep test names); add one test: `cookie is scoped to the server port`.

### Explicitly out of scope
- Every other follow-up. The UI (Phase 2) relies on the cookie only through the browser, so no UI
  file changes.

## Implementation steps

1. Change both cookie-name sites in `server.mjs`. Escape nothing by hand: the port is an integer.
2. Update the existing tests that build or check `taskify_t=…`.
3. Add `cookie is scoped to the server port`: start two servers (port 0 each, different tokens).
   For server A send the stray cookies carrying A's own token, `cookie: taskify_t_<B port>=<A token>;
   taskify_t=<A token>` → `401` (A must ignore them by name, not because the token is wrong); send
   `taskify_t_<B port>=<B token>; taskify_t_<A port>=<A token>` → `200`. Check `Set-Cookie` from
   `/?t=` names A's port.
4. Run the ACs.
